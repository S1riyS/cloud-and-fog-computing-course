# Практическая работа 4. Docker Swarm

-----------------------------------

**Цель:** Развернуть отказоустойчивый стек контейнеров, исследовать петлю согласования (reconciliation loop), динамическое масштабирование и поведение Routing Mesh при авариях.

**Время:** 90 минут

**Формат сдачи:** Отчет PDF с зафиксированными состояниями сервисов и логами восстановления после сбоя.

Помимо стандартных `Running` и `Failed` , оркестратор Swarm проводит задачу через богатый граф состояний (Task States), которые видны через `docker service ps` :

1. **`Pending`** — задача создана, но ждёт назначения на ноду (нет свободных ресурсов, скачивается тяжелый Docker-образ).

2. **`Preparing` / `Starting`** — стадия инициализации, выполнения healthcheck или `ENTRYPOINT` . Контейнер еще не принимает входящий трафик (critical для zero-downtime деплоев).

3. **`Shutdown` / `Complete`** — штатное завершение задачи (например, при масштабировании вниз или завершении cron-задачи).

4. **`Rollback`** — состояние автоматического отката сервиса, если новая версия упала при Healthcheck.

Создайте файл docker-stack.yml  

version: '3.8'  
services:  
 web:  
  image: python:3.11-alpine  
  environment:  
   - TASK\_SLOT={{.Task.Slot}}  
  command:  
   - "python"  
   - "-u"  
   - "-c"  
   - "import http.server, socket, os; server = http.server.HTTPServer(('0.0.0.0', 5678), type('H', (http.server.BaseHTTPRequestHandler,), {'do\_GET': lambda s: (s.send\_response(200), s.send\_header('Content-Type', 'text/plain; charset=utf-8'), s.end\_headers(), s.wfile.write(f'Hello from Swarm! Container ID: {socket.gethostname()} | Slot: {os.environ.get(\\"TASK\_SLOT\\", \\"N/A\\")}\\\\n'.encode()))})); server.serve\_forever()"  
  ports:  
   - target: 5678  
    published: 8080  
    protocol: tcp  
    mode: ingress  
  deploy:  
   replicas: 3  
   restart\_policy:  
    condition: on-failure

ЭТАП 0. Подготовка и инициализация кластера (10 минут)
------------------------------------------------------

1. Убедитесь, что Docker Desktop запущен и в режиме Linux Containers.

2. Инициализируйте локальный одноузловой Swarm-кластер:

    docker swarm init --advertise-addr 127.0.0.1

3. Создайте рабочую директорию `swarm-lab` , сохраните в неё исправленный файл `docker-stack.yml` и разверните стек:

    docker stack deploy -c docker-stack.yml web-stack

4. Убедитесь, что сервис успешно запущен (должно быть 3 реплики):

    docker stack services web-stack

    `docker service ps web-stack_app-node`

ЭТАП 2. Динамическое масштабирование (Scaling Up / Down) (20 минут)
-------------------------------------------------------------------

В реальной практике нагрузка на сервисы меняется, и оркестратор должен мгновенно реагировать на изменение желаемого состояния (Desired State).

1. **Масштабирование вверх (Scale Up):** Увеличьте количество реплик до **6** :

    docker service scale web-stack\_app-node=6

2. Проследите за процессом создания новых задач в реальном времени:

    docker service ps web-stack\_app-node

    _Зафиксируйте, через какие промежуточные состояния (`Pending` _\->_ `Starting` _\->_ `Running` ) проходят новые контейнеры._

3. **Масштабирование вниз (Scale Down):** Верните количество реплик к **2** :

    docker service scale web-stack\_app-node=2

    _Посмотрите, как Swarm корректно завершает лишние задачи (состояния `Shutdown`  -> `Complete` )._

ЭТАП 3. Хаос-инженерия и Петля согласования (Reconciliation Loop) (25 минут)
----------------------------------------------------------------------------

Проверим способность оркестратора к самовосстановлению (Self-healing).

1. Установите количество реплик равным **3** .

2. Откройте второе окно терминала и запустите мониторинг задач в цикле:

    watch -n 1 docker service ps web-stack\_app-node

3. В первом окне найдите имя или ID одного из запущенных контейнеров реплики:

    docker ps | grep web-stack

4. Принудительно уничтожьте контейнер:

    docker rm -f <CONTAINER\_ID\_OR\_NAME >

5. Наблюдайте в окне мониторинга, как Swarm фиксирует сбой задачи (`Failed` ), переводит её в `Shutdown` и мгновенно создает новую задачу для поддержания Desired State ( **3**  реплики).
