# Практическая работа 6. MicroShift

## Практическое занятие: Управление ресурсами и жесткими квотами на Edge-узлах (MINC / MicroShift)

**Цель:** Изучить поведение легковесного оркестратора при дефиците ресурсов, настроить `resources.limits` и `resources.requests`, исследовать механизмы предотвращения сбоев (`OOMKilled`) и применить пространственные квоты (`ResourceQuota`) в среде MINC (MicroShift in Container).

**Время:** 90 минут

**Инструмент:** MINC (MicroShift) + `oc` / `kubectl` (`kubectl` можно использовать во всех следующих командах вместо `oc`)

**Формат сдачи:** Инженерный отчет с логами событий `OOMKilled`, описанием инцидентов перегрузки и конфигурационными манифестами.

**Максимальный балл:** 6 баллов.

## Контекст: Почему квоты критичны на Периферии (Edge)?

В отличие от дата-центров с избыточными ресурсами, Edge-устройства (шлюзы, промышленные контроллеры, локальные серверы) имеют строго лимитированную память и процессор. Если один неуправляемый микросервис забьет всю операционную память (OOM), пострадают критически важные соседние процессы (например, сбор телеметрии с датчиков). Оркестраторы семейства OpenShift / MicroShift используют жесткие механизмы изоляции и квотирования (`Requests`, `Limits`, `ResourceQuota`), чтобы гарантировать стабильность системы.

## ЭТАП 0. Подготовка локального стенда MINC (15 минут)

Развернем легковесный кластер OpenShift-совместимого API внутри изолированного контейнера через MINC.

1. Убедитесь, что у вас установлены **Podman** (в rootful-режиме) или **Docker**, а также утилиты `oc` / `kubectl`.
2. Скачайте и установите утилиту `minc` (для вашей ОС):

    Пример для Linux / macOS:

    ```bash
    curl -LsSf -o minc https://github.com/minc-org/minc/releases/latest/download/minc_linux_amd64
    chmod +x minc && sudo mv minc /usr/local/bin/
    ```

3. Создайте и запустите кластер MINC (если используете podman, то `-p docker` можно убрать):

    ```bash
    minc create -p docker --disable-overlay-cache
    ```

4. Сгенерируйте и привяжите файл конфигурации для доступа через `oc`:

    ```bash
    minc generate-kubeconfig
    ```

5. Проверьте работоспособность узла:

    ```bash
    oc get nodes
    ```

## ЭТАП 1. Изучение бесконтрольного потребления и OOM-Kill (20 минут)

Смоделируем ситуацию, когда приложение без лимитов исчерпывает память узла.

1. Создайте изолированное пространство имен (namespace) для изоляции эксперимента:

    ```bash
    oc create namespace edge-test
    ```

2. Создайте манифест `memory-hog.yaml` для приложения, которое циклично выделяет память в оперативной памяти без освобождения:

    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: memory-hog-pod
      namespace: edge-test
    spec:
      containers:
      - name: memory-eater
        image: python:3.9-slim
        command: ["python", "-c", "import time; a = []; [a.append(' ' * 10**7) for i in range(1000)]; time.sleep(300)"]
    ```

3. Примените манифест и запустите мониторинг статуса подов в реальном времени:

    ```bash
    oc apply -f memory-hog.yaml
    oc get pods -n edge-test -w
    ```

4. **Анализ результата:** Через несколько секунд вы заметите, что статус пода изменился на `OOMKilled` (Out of Memory), а счетчик `RESTARTS` увеличился.
5. Проверьте детали события через `oc describe`:

    ```bash
    oc describe pod memory-hog-pod -n edge-test
    ```

    Зафиксируйте в отчете строку с причиной завершения: `OOMKilled: true`.

## ЭТАП 2. Настройка Requests и Limits (Quality of Service) (20 минут)

Научим оркестратор защищать систему с помощью явного указания квот на уровне контейнера.

1. Удалите старый под:

    ```bash
    oc delete pod memory-hog-pod -n edge-test
    ```

2. Создайте защищенный манифест `resource-limited-pod.yaml`, добавив секцию `resources`:

    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: limited-pod
      namespace: edge-test
    spec:
      containers:
      - name: constrained-app
        image: python:3.9-slim
        command: ["python", "-c", "import time; print('Running within limits'); time.sleep(300)"]
        resources:
          requests:
            memory: "64Mi"
            cpu: "100m"
          limits:
            memory: "128Mi"
            cpu: "500m"
    ```

3. Примените манифест:

    ```bash
    oc apply -f resource-limited-pod.yaml
    ```

4. Проверьте присвоенный класс обслуживания (QoS Class):

    ```bash
    oc get pod limited-pod -n edge-test -o jsonpath='{.status.qosClass}'
    ```

    Объясните в отчете, почему этот под получил класс `Burstable`.

## ЭТАП 3. Установка Namespace-level ResourceQuota (20 минут)

На периферии часто развертываются сторонние компоненты. Администратор должен ограничить суммарное потребление ресурсов всего namespace.

1. Создайте манифест `quota.yaml`:

    ```yaml
    apiVersion: v1
    kind: ResourceQuota
    metadata:
      name: edge-env-quota
      namespace: edge-test
    spec:
      hard:
        requests.cpu: "500m"
        requests.memory: "256Mi"
        limits.cpu: "1"
        limits.memory: "512Mi"
        pods: "3"
    ```

2. Примените квоту:

    ```bash
    oc apply -f quota.yaml
    ```

3. Проверьте статус примененной квоты:

    ```bash
    oc describe resourcequota edge-env-quota -n edge-test
    ```

4. **Попытка нарушения квоты:** Попробуйте развернуть второй под, требующий `400Mi` памяти (что превышает жесткий лимит namespace `256Mi`).

    Зафиксируйте ошибку валидации, которую вернет API-сервер MINC.

Составьте и сдайте краткий отчет по результатам практической работы.

2. **Логи OOM-Kill:** Приложите фрагмент вывода `oc describe pod` для этапа №1, где зафиксирован сбой `OOMKilled`.
