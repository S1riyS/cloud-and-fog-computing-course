# ЛР2. Корреляция трёх источников (логи, метрики, трейсы)

Студент: Анкудинов Кирилл Константинович (413732) · Группа: OTV1 · Стек: **ELK + Prometheus + Jaeger**

## Цель

Получить тикет «в HH:MM пользователи получили ошибки 5xx» и восстановить причинно-следственную цепочку, проходя путь **trace → log → metric**. Результат: incident timeline, найденная первопричина, исправление и количественное доказательство, что оно сработало.

Не сводите работу к «посмотрел один дашборд»: каждый вывод должен подтверждаться данными из источников, а не догадкой. В вашем стенде есть как минимум одно расхождение между источниками, и ему посвящена отдельная часть отчёта.

## Требования

- Docker с Compose v2, `bash`, `curl`; Windows: WSL2. Желательно `python3`.
- Не менее 8 ГиБ RAM на машине, доступно Docker не менее 6 ГиБ. Первый запуск: 5–10 минут и несколько гигабайт загрузки образов.
- Срок выполнения: 2 месяца; плановая трудоёмкость около 3 часов.

## Состав стенда

`gateway → orders → payments`, PostgreSQL, Redis. Логи: Filebeat → Elasticsearch → Kibana. Метрики: Prometheus (cAdvisor, exporters). Трейсы: OpenTelemetry → Jaeger (хранение в памяти). Адреса интерфейсов см. в `variant.md`. Приложение пишет JSON-логи с полями `ts`, `level`, `service`, `message`, `trace_id`, `request_id`, `order_id` и др.

## Где что смотреть

- **Логи:** Kibana → Discover, data view `app-logs`. Время события берётся из поля `ts`.
- **Трейсы:** Jaeger UI → Service `gateway` → Find Traces; поиск по тегам и trace ID.
- **Метрики:** Prometheus → Graph; cAdvisor: <http://localhost:8081>.

## Что понадобится

- Метрики Prometheus: `http_requests_total`, `http_request_duration_seconds`, `db_pool_*`, `cache_*`, `payments_*`, а также метрики cAdvisor и exporters. Пример: `sum by (service, status) (rate(http_requests_total[1m]))`.
- Логи: ищите по `trace_id`, `request_id`, `order_id`, `level`, `service`.
- Данные пострадавших пользователей берите из логов gateway (поле `user_id`, `status`).
- Изменения `.env` и конфигов применяются командой `bash scripts/up.sh`. Команды к БД: `docker compose exec postgres psql -U app -d shop`.
- Время указывайте в UTC. Проверьте, что вы сравниваете одинаковые временные шкалы.

## `evidence.json`

Заполните поля (допустимые значения для перечислимых полей перечислены в `_allowed`):

| Поле | Содержание |
|---|---|
| `run_id` | `run_id` из `evidence/loadgen_result.json` |
| `first_error_time_utc` | время первого 5xx, ISO-8601 в UTC |
| `users_affected` | число уникальных пользователей, получивших 5xx |
| `failing_service`, `root_cause_class` | где первопричина и её класс |
| `key_metric` | `query` (запрос) и `peak_value` (пиковое значение метрики, подтверждающей причину) |
| `trap_class` | класс найденного расхождения между источниками |
| `trace_ids` | идентификаторы 2–3 трейсов упавших запросов (с вашего прогона) |
| `changes` | что вы изменили: `what`, `old`, `new` |

## Правила

- Работа индивидуальная. Результаты прогона привязаны к вашему варианту подписью, чужие артефакты не принимаются.
- Не изменяйте `app/loadgen/` и файлы `evidence/loadgen_*.json`.
- Нагрузка до и после исправления одинаковая (тот же объём запросов); сравнивайте результаты на одинаковых условиях.
- Отчёт оценивается по доказательствам: приводите команды, запросы и их вывод.
